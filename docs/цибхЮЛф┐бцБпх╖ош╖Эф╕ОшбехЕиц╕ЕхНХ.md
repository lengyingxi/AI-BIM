# 本模型 vs 传统 BIM 运维模型：信息差距与补全清单

> 对照对象：滨海科创中心 A 座（`web/data/model-data.js`，5 层 / 2574 m²）
> 参照标准：IFC4（ISO 16739）、COBie（设施管理交付）、GB/T 51269-2017（建筑信息模型分类和编码标准）、GB/T 51212-2016（BIM 应用统一标准）

---

## 一、这份模型现在到底有什么

| 项 | 数量 / 内容 |
|---|---|
| 楼层 | 5 层，层高 4.5 / 3.9 / 3.9 / 3.9 / 3.9 m，屋面 20.1 m |
| 房间 | 55 间（每层 11 间：南 5 + 北 5 + 走廊 1），面积 43.56 m²，另有 6.6×2.4 走廊 |
| 结构 | 框架柱 120、框架梁 50、楼板 55；轴网 6.6×6.6 |
| 建筑 | 墙 70（外墙 250 / 走廊隔墙 200 / 内隔墙 200）、门 51、窗 54（C1818，台高 0.9） |
| 机电 | 风管 50 段、风阀 55 个（楼层总阀 / 分区阀 / 支管阀，带 `parent` 与 `serves`） |
| 设备 | 12 类设备库（0.35 t 实验台 ~ 4.50 t 风冷冷水机组），含重量、外形尺寸 W×D×H |
| 结构参数 | 板厚 120/180/200 mm、混凝土 C30、配筋 φ12@150 / φ14@150、保护层 20、活荷载 2.0~7.0 kN/m² |

**已经具备的"关系型"信息**（这是它比一般演示模型强的地方）：

- 空间归属：`room.sides` 记 4 面墙 id；墙 / 门 / 窗带 `rooms`；阀带 `room`
- 系统拓扑：阀 → 父阀 → 服务的支管；风管按段首尾相接，可做"关阀查下游影响"
- 结构可算：配筋、板厚、活荷载齐全，能出单板承载力计算书（GB 50010 口径）
- 可编辑：门 / 窗 / 墙洞口能实时改，改完立刻重算开门碰撞与承载

**一句话结论**：这是一份**"几何 + 结构校核"模型**，不是**"运维资产"模型**。
它在一个维度（结构配筋）上比常规建筑 BIM 更细，但在设施管理（FM）维度上几乎是空白。

## 二、逐维度差距表

差距等级：`—` 完全没有｜`弱` 有但不完整｜`有` 基本满足

| # | 维度 | 传统 BIM 运维模型要求 | 本模型现状 | 等级 |
|---|---|---|---|---|
| 1 | 身份标识 | 每构件 GlobalId(GUID)、IfcClass、分类编码（GB/T 51269）、版本号 | 自编 id（`W-1F-001` / `EQP1`），无 GUID、无分类编码、无版本 | — |
| 2 | 空间结构 | IfcBuilding/Storey/Space 层级，空间 Name/Number/LongName/Zone | 有 floor / room / zone（south/north/corr/core），无 IfcSpace 语义 | 弱 |
| 3 | 空间边界 | IfcRelSpaceBoundary，墙-空间面级关联、面积/体积 | 墙-房间是 id 列表，无面积/体积/朝向量化 | 弱 |
| 4 | 几何精度 | LOD300~350，构件按真实断面与构造做法 | 程序化体量：墙为板、门为板、风管带法兰/支吊架、设备有 8 材质槽细节，但无内部构造 | 弱 |
| 5 | 材料与做法 | IfcMaterialLayerSet：层次、厚度、保温、防火、面层、密度 | 只有混凝土强度等级 C30 / 钢筋 HRB400 | — |
| 6 | 防火与耐火极限 | 构件耐火等级、防火分区、疏散距离 | 无 | — |
| 7 | 结构与荷载 | 构件截面、荷载、设计依据 | **有**：配筋、板厚、活荷载、安全等级二级、50 年 | 有 |
| 8 | 机电系统 | IfcDistributionSystem 命名、介质、系统分区、设备-管-末端连通 | 有管段与阀的父子/服务关系，无系统命名与介质属性 | 弱 |
| 9 | 设备资产台账 | 类型-实例两级（COBie Type/Component）：厂家、型号、序列号、额定功率、风量/冷量、噪声、重量、生产日期 | 只有名称、重量、外形尺寸、颜色 | — |
| 10 | 安装信息 | 安装日期、安装单位、验收人、保修起止、原值/折旧 | 无 | — |
| 11 | 维护信息 | 保养周期、保养项、备件清单、专用工具、上次/下次维护 | 无 | — |
| 12 | 工单与故障 | 工单编号、故障码、处理记录、MTTR/MTBF | 无 | — |
| 13 | 运行数据 | BA/BAS 点位、实时功率、供回水温度、运行时长 | 无（本原型离线，不接实时数据） | — |
| 14 | 传感器/物联网 | 点位表、协议、通信地址、告警阈值 | 无 | — |
| 15 | 合规与证照 | 特种设备使用登记证、消防验收、压力容器、年检记录 | 无 | — |
| 16 | 变更与版本 | 模型版本、变更单、竣工版 vs 现状版 | 无（改完只在本会话内存里，刷新即回到初始） | — |
| 17 | 文档挂接 | 图纸、说明书、合格证、隐蔽工程照片 | 无 | — |
| 18 | 标识与定位 | 二维码/RFID、机房编号、货架位 | 无 | — |
| 19 | 空间使用 | 租户、部门、工位号、人数、使用状态 | 有房间用途（`use`），无租户/工位/人数 | 弱 |
| 20 | 数据交付格式 | IFC4 + COBie（xlsx）+ 点云/实景 | 自研 JSON（约 4.6 万行数据），另有 IFC4 导出器（无属性集内容） | 弱 |

### 最要紧的三条

1. **没有 GUID / 分类编码** —— 一旦要和真实资产台账、工单系统、门禁/BA 对上号，全靠名字猜，一改名字关系就断。
2. **设备只有"重量和长宽高"** —— 运维真正天天用的型号、功率、厂家、保修期、序列号，一个都没有。
3. **没有维护与时间维度** —— 运维模型的核心是"什么时候该做什么"，这份模型里没有时间轴。

## 三、要补成"运维模型"，谁来做、做什么

### A. 必须人工（AI 替不了，或替了要担责）

| 任务 | 为什么必须人 |
|---|---|
| 现场实测核对（设备实际位置、标高、管线走向偏差） | AI 无法获得现状真值；规范允许偏差需人工判定 |
| 设备铭牌信息（型号、序列号、额定参数） | 需要现场拍照确认或查合格证，错一个字段就是资产错账 |
| 资产财务口径（原值、折旧年限、残值） | 财务口径由业主/财务确定 |
| 法定责任信息（特种设备登记、消防验收、责任人和签字） | 有法律效力，必须实名签认 |
| 系统划分与命名规则的**最终裁定** | AI 能给建议方案，拍板要人 |
| 验收签认与交付确认 | 交付节点责任 |

### B. AI / 自动化能做（占总量的大头）

| 任务 | 做法 | 预期自动化率 | 人工要做的事 |
|---|---|---|---|
| 补 GUID + IFC 实体类型 + 分类编码 | 规则 + 已有 id 映射，批量生成并写回 JSON/IFC Pset | ~100% | 抽查 5% |
| 由几何自动推断空间归属 | 点在多边形内 + 墙轴线投影（本模型已用此法做门/窗/风管归属） | ~95% | 处理跨房间构件 |
| 由拓扑推断系统划分 | 图连通分量：管段-阀-设备三色图，按楼层/分区聚类命名 | ~85% | 确认分区边界 |
| 从设计图 PDF / 扫描件抽构件表 | OCR + 版面分析 + 表格结构化 | ~70% | 逐条校对 |
| 从铭牌照片抽设备参数 | 视觉模型识别铭牌字段 | ~80% | 抽检 + 补漏 |
| 维护周期模板生成 | 按设备类型套行业知识库（空调季检、水泵月检…） | ~90% | 按厂家手册修订 |
| 备件清单生成 | 按设备类型 + 易损件库 | ~70% | 补本地库存 |
| 命名规范化与去重 | 规则 + 相似度聚类（`M1021` 与 `M1021(1)`） | ~95% | 确认合并 |
| 生成 COBie 三张核心表（Type / Component / Space） | 从上面结构化数据导出 | ~100% | 交付前审阅 |
| **主动发现缺什么** | 一致性规则扫描：每扇门必属 1~2 空间、每台设备必属 1 空间且有可通行门、每个阀必有父与服务对象 | ~100% | 处理告警 |

### C. 一致性规则（建议直接做成系统校验，就是"AI 主动提问"的触发条件）

1. 每台设备必须属于 1 个空间，且 `min(w,d)+0.12 ≤ 该空间某扇门的净宽`，`h+0.08 ≤ 门高`（**本原型已实现为 `C.passDoor` + 拓门询问**）
2. 每扇门必须连接 1~2 个空间，且门扇 0.9 m 开启范围内无设备（**已实现为 `C.door` 校核**）
3. 每个阀必须有 `parent`（除楼层总阀）与 `serves` 非空
4. 每段风管至少属于 1 个空间（**已实现为 `ductRooms` 索引**）
5. 设备落位不得与柱、梁下净高、阀件检修位、家具、既有设备检修通道冲突（**已实现为 `C.obstruct` 8 类检查**）
6. 设备必须有厂家/型号/序列号/保修期四要素，缺一即告警
7. 每台特种设备（压力容器、电梯、消防泵）必须有证照编号与下次年检日期

## 四、建议的补全路线

| 批次 | 内容 | 预估工作量 | 谁主导 |
|---|---|---|---|
| 1 | 身份与分类：GUID、IFC 类型、GB/T 51269 编码、命名规范化 | 2~3 人日 | AI 全自动 + 人工抽查 |
| 2 | 设备台账：型号/功率/厂家/序列号/保修，及设备-空间-系统三向关联 | 5~8 人日（含现场拍照） | AI 抽取 + 现场补录 |
| 3 | 系统与拓扑补全：风系统命名、末端风口、阀-末端对应、服务房间清单 | 3~5 人日 | AI 推断 + 人工确认 20% |
| 4 | 运维业务：维护计划、备件、责任人、二维码、工单接口 | 10 人日以上 | 人工主导，AI 出模板与排程 |
| 5 | 交付：导出 IFC4（带 Pset）+ COBie xlsx + 数据字典 | 2 人日 | AI 导出 + 人工审阅 |

## 五、这套原型为什么是现在这个样子（技术取舍）

| 取舍 | 原因 | 代价 |
|---|---|---|
| 几何全部程序化生成，不用外部模型库 | 要求**全离线可运行**、单机断网可用 | 构件是"参数化体量"，不是真实剖面；LOD 约 300 |
| 数据是自研 JSON 而不是直接吃 IFC | 要能**实时改门改墙、实时重算**承载与碰撞；IFC 改一处要重建整个模型 | 与 IFC/COBie 生态不直连，需要一层导出映射 |
| 承载力/开门/碰撞用自研 GB 口径公式 | 要能解释"为什么不行"，而不是只给红绿 | 只覆盖单板局部承压与门洞净距，不做整体结构分析 |
| 不接实时数据（BA/能耗/传感器） | 离线原型 | 第 13~14 项差距无法在原型内体现 |
| 改动只存在内存里 | 避免离线环境引入数据库 | 第 16 项（版本与变更）必须由外部系统承担 |

## 六、怎么验证补得对不对

| 项 | 方法 | 合格线 |
|---|---|---|
| 几何位置 | 现场抽测 30 处，与模型坐标比 | 偏差 ≤ 5 cm |
| 设备台账 | 铭牌字段逐字段比对 | 关键字段一致率 ≥ 98% |
| 空间归属 | 每台设备人工确认所属房间 | 无错归属 |
| 系统拓扑 | 关一个阀，比对"模型预测受影响房间"与"现场实测无风房间" | 一致率 ≥ 95% |
| 规则一致性 | 跑第二节 C 的 7 条规则 | 0 条未处理告警 |

## 七、本轮已经落进代码的"自动推断"能力（可作为补全的起点）

| 能力 | 位置 | 说明 |
|---|---|---|
| 构件→空间归属（门/窗/风管） | `web/js/tree.js` `doorsOfRoom / windowRoom / ductRooms` | 几何 + 拓扑双重判定，解决"一堵隔墙挂 10 扇门"的脏关系 |
| 设备能否搬进房间 | `web/js/calc.js` `C.passDoor` | 最小包裹尺寸 vs 门洞净宽/净高 |
| 设备与周边 8 类碰撞 | `web/js/calc.js` `C.obstruct` | 房间边界、框架柱、既有设备、上方风管净高、阀件、门扇开启、家具、采光 |
| 家具真实占位 | `web/js/detail.js` `D.furnRects` | 建家具时记录落位矩形，供碰撞校核 |
| 空间树（BIM 式层级） | `web/js/tree.js` | 项目 → 楼层 → 房间 → 楼板/墙/门/窗/设备 + 结构/通风空调 |
| 门洞拓宽的合规校验 | `web/js/app.js` `doWidenDoor` | 先过 `C.door` 校核（墙角、邻门、柱、风管、设备挡门），过不了就不改 |
